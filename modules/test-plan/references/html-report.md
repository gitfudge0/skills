# Formal HTML test report

Use package-root `shared/report-deck/guide.md` for the shared plan runtime, packing, theme, comments, response copying, printing and output verification. Read `../assets/example.src.html` for test-report structure; `../assets/example.html` is its portable packed preview. Keep the canonical UI rather than adding a stylesheet or theme script. In source the template links `../../../plan/runtime/`; installed packages supply `shared/report-deck/runtime/` and its packer resolves the canonical assets by filename. Pack the source with the applicable runtime's `pack.mjs` into a single offline HTML document.

## Content contract

- Put the report title, mode, revision (`v1`, `v2`, etc.), observed tally, and evidence limits in the header and first summary claim. A plan-only report is titled “Test case matrix”; every case is `NOT RUN — PLANNED — not executed`, with zero passed and failed. Name a pending decision only if one remains. The report does not create an approval gate.
- Make the matrix the main content. Use stable case IDs on `doc-claim` elements, grouped by test tier where useful. A native table is also suitable for a short matrix. Preserve typed IDs, priority, title, scenario/setup/action, expected result, execution requirements, status, not-run reason and recorded evidence. Show Protects when applicable. Use the shared `dl.kv`, table and explicit text pills; colors supplement status labels.
- Preserve agreed IDs and expected outcomes across result revisions. A `PASS` requires observed evidence; a `FAIL` includes the actual result and a pointer to failing output or the exposed bug. `NOT RUN` includes its concrete reason. Missing command output or run identity stays explicitly missing; copying a fixture does not establish execution.
- Keep the strategy, applicable coverage categories, gaps with consequence, blocked cases and out-of-scope exclusions visible as summary or auxiliary claims. Separate not applicable from not covered. Include the current plan/results version and evidence revision/environment when available.
- Example data is fictional. Replace it with actual scoped cases and evidence; do not inherit its claimed outcomes. Plan-only output does not authorize test implementation or execution.

The runtime supplies navigation, claim comments, Copy response, light/dark themes and print behavior. Report comments are feedback, not test execution, build or publication approval. Use no `doc-ask` merely to make a report interactive. Keep report facts in document content; feedback does not overwrite the authoritative plan or results. The packer's plan-specific advice about claim count, heading sentences or exhibits is advisory for reports; do not drop cases or fabricate exhibits to silence it.

Save the packed document at the exact caller override, or resolve a unique `test-plan` path using package-root `shared/artifacts.md`. Open it with an available browser tool or platform opener, verify rendering and all cases, then return its path. A chat-only plan creates no HTML.
